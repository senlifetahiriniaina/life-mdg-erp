# Life MDG ERP - Claude Code Configuration

## Project Overview

Life MDG ERP is a Laravel 12 + Vue 3 modular ERP, extracted and trimmed from the WideHalo ERP platform for Life MDG's own launch. It keeps WideHalo's seven founding principles, scoped to the modules Life MDG actually needs to start:

| Principle | Definition |
|---|---|
| **Africa First** | OHADA/SYSCOHADA, mobile money (Orange Money, MTN MoMo), CFA Franc, i18n |
| **Asia First** | Multi-currency/timezone, i18n (10 languages shipped in `lang/`) |
| **API First** | All features exposed as REST API before any UI |
| **Compliance First** | GDPR, PDPL, OHADA, OWASP by design |
| **Simplicity First** | Onboarding wizard (Setup module), smart defaults, AI-assisted import |
| **AI Assisted First** | Claude embedded at every friction point via `AiContextualAssistantService` |
| **Strategy First** | KPI/ratio cockpit, benchmarks, correlations, AI strategic recommendations |

## Scope: 27 modules

Extracted from the WideHalo ERP monorepo (`Widehalo-ERP`, 49 modules). Everything not listed below (Manufacturing, POS, Ecommerce, Email, WhatsApp, Documents, Planning, Quality, PLM, Discussion, Assets, Contracts, SMS, SmartTable, Notes, CustomerService, MarketingAutomation, RealTime, MobileSync, Messaging, and HR's advanced ATS/performance/training/succession features) was intentionally left out.

**Socle CORE / système (12)**: Core, AI, Security, AuditLog, API, Integration, Validation, Shared, Settings, Setup, Workflow, Calendar
**Compta et Finance**: Accounting
**Commercial et CRM**: CRM, Sales
**Stock et Logistique**: Inventory, Logistics, Achats
**Pilotage et Reporting**: BI, Analytics, Reporting, Strategy
**RH basique**: HR (trimmed — see below), Payroll, Timesheets, Projects
**Support**: Helpdesk (full, coupled to the other modules — see below)

### HR: "basique" scope only

`Modules/HR` kept only: `Employee, Department, Position/JobPosition, Attendance*, ShiftSchedule, BiometricDevice, LeaveRequest, LeaveBalance, LeaveType, LeaveApprovalLog, TimeOffRequest, EmployeeDocument, EmployeeSkill/Skill, CompensationHistory, SalaryBand, EmployeeCompensation, Deduction` plus their controllers/services/policies/tests. ATS/recruitment, 360° performance reviews, training catalogue, succession/org chart, advanced benefits, and engagement surveys were removed (not needed for launch) — including a duplicate legacy Payroll implementation that lived inside HR (the dedicated `Payroll` module is the single source of truth for payroll).

### Helpdesk: coupled to every other module

Any record in `Accounting\Invoice`, `CRM\Contact`, `Inventory\Product`, `Sales\SalesOrder`, `Achats\PurchaseOrder`, `Projects\Project`, `Logistics\Shipment`, or `HR\Employee` can raise and list its own tickets via the `Modules\Helpdesk\Traits\HelpdeskLinkable` trait:

```php
$invoice->raiseTicket(['subject' => 'Facture erronée', 'priority' => 'high']);
$invoice->tickets; // tickets linked to this invoice
```

`POST /api/v1/helpdesk/tickets` accepts an optional `source_module`/`source_id` pair (validated against an allowlist morph-map registered in `HelpdeskServiceProvider` — never a raw class name from client input) to link a new ticket to any record. A global "Signaler un incident" button (`resources/js/Components/Helpdesk/QuickTicketButton.vue`) is embedded in `AppLayout.vue` so any authenticated user can raise a ticket from anywhere in the app. To make a new module's model linkable, add the `HelpdeskLinkable` trait and register its morph-map alias.

## Repository Structure

```
/
├── app/                    # Root Laravel app (real entry point — NOT apps/api or apps/webapp, which don't exist here)
├── Modules/                # 27 ERP modules (laravel-modules / nwidart)
├── resources/js/           # Vue 3 + Inertia frontend (real entry: resources/js/app.js)
├── database/
│   ├── migrations/         # Root migrations (schema shared across modules)
│   └── seeders/            # RolesAndPermissionsSeeder is the active RBAC seeder
├── lang/                   # i18n dictionaries: ar, en, es, fr, ha, hi, mg, pt, sw, zh
├── tests/                  # Root Unit/Feature/Integration tests
└── config/, routes/, bootstrap/   # Standard Laravel
```

Each module self-registers its own routes via its `RouteServiceProvider` — `routes/api.php` at the root only holds global routes (health, auth, dashboard, AI chat, admin). Removing a module is `rm -rf Modules/<Name>` plus an entry removed from `config/modules_statuses.json`; no manual route wiring needed elsewhere.

## Development Workflow

**Backend (Laravel API):**
```bash
composer install
cp .env.example .env && php artisan key:generate
php artisan migrate --seed

vendor/bin/pest                  # Run all tests
vendor/bin/pest --filter=TestName
```

**Frontend (Vue 3):**
```bash
npm install

npm run type-check
npm run lint
npm run build
npm run test                     # Vitest unit tests
```

## Known gaps (not blocking launch, tracked here rather than silently left)

- **`composer.json`** intentionally drops the `widehalo/core`/`widehalo/modules` requires and their `.widehalo-core` path-repositories that Widehalo-ERP carried — nothing in the app code actually imports from that namespace (confirmed by grep across the whole tree before removing it), so it was dead weight.
- **`Dockerfile` now builds cleanly** — the `docker/{supervisor.conf,php.ini,php-fpm.conf,health-check.php}` gap tracked here previously has been closed: `docker/` now contains real infrastructure content (PHP-FPM pool tuned for the container's non-root `appuser`, OPcache/limits tuning, a supervisord fragment launching `php-fpm` in the foreground, and a TCP-connect health check against the exposed port 9000). Confirmed via a real `docker-build.yml` CI run, not just a local lint. The gitignored-lockfile and dead-`.widehalo-core` COPY lines were fixed earlier (matching the same fixes applied to `.github/workflows/`).
- **`composer.lock` / `package-lock.json` are gitignored** (matching Widehalo-ERP's own convention) — run `composer install` / `npm install` fresh (not `npm ci`, which requires a lockfile to already exist rather than generating one — this bit CI too, see the GitHub Actions workflows' commit history); `nunomaduro/larastan` (dev-only, static analysis) may need a working GitHub API connection to install depending on your network — it is not required to run the app or the test suite.
- **Most of what was originally flagged here as "incomplete in the source Widehalo-ERP repo" has since been built for real**, not just documented: multi-company Consolidation now lives behind a single unified `Modules\Accounting\Models\ConsolidationGroup` (the parallel `ConsolidationHierarchy` stack was kept too — it's a genuinely different concept, an ownership tree with periods/eliminations — and wired up rather than deleted); the Budget-variance models (`BudgetActual`, `BudgetAlert`, `BudgetForecast`, `GLEntry`) and Security's compliance-audit models (`ComplianceAudit`, `ComplianceViolation`, `EncryptedField`, `EncryptionKey`, `ServiceIdentity`, `TrustZone`) all reconnected cleanly once the root `App\Models\Company` foundation landed. **ASC606 Revenue Recognition (`RevenueRecognitionEvent`/`RevenueContract`) is the one exception, explicitly excluded rather than built**: it's the US-GAAP five-step revenue-recognition standard (performance-obligation allocation, variable-consideration constraint, contract-liability schedules) — Life MDG keeps its books under OHADA/SYSCOHADA, which has no equivalent concept, so there is nothing to port. `Modules/Accounting/tests/Feature/RevenueContractTest.php`'s 5 failures are this gap, not a regression.
- **Strategy module's `training_roi`/`time_to_fill` HR ratios** return static fallback values (145.0 / 28 days) since they depend on the Training/ATS features that are out of scope — this was already the design pattern used throughout `KPIRegistryService` for any data source that might not exist (every KPI query is wrapped in try/catch with a fallback), so it degrades the same way the rest of the app does when a data source is thin.
- **`Modules/Projects`' wiki feature was removed** (depended on the excluded `Notes` module) rather than decoupled with a stub — it was a self-contained side feature (`ProjectWikiService`/`ProjectWikiController`), not core project management.
- **A security audit surfaced several gaps, now fixed** (see `docs/09-RBAC-SECURITE/STANDARDS-SECURITE-MADAGASCAR.md` for the full state and traceability): `Modules\Core\Services\SecretsService`'s AES-256-CBC secrets vault is backed by a real `Modules\Core\Services\EncryptionService`/`KeyManagementService` pair; the federation endpoints (`/api/v1/federation/*`) are protected by a real `VerifyFederationSignature` middleware (HMAC-SHA256 + anti-replay); mandatory TOTP 2FA roles are config-driven (`config('security.mandatory_2fa_roles')`) rather than hard-coded to admin/super-admin; all controllers extend `App\Http\Controllers\Controller`; `session.security` middleware (device fingerprint/hijack detection) is rolled out across all 27 modules' route groups, not just HR.
- **GraphQL (Lighthouse) is now wired up as a single real schema** — `project/graphql/schema.graphql` (CRM contacts/accounts to start, with `@paginate`/`@guard`/explicit resolver classes) is what `config/lighthouse.php:76`'s `schema_path` actually points at. This replaced a second, parallel "GraphQL v2" stack (`Modules\API\Services\GraphQLSchemaBuilderService`/`GraphQLQueryOptimizerService`/`GraphQLSubscriptionManagerService`) that stored hand-rolled schema fragments in `Cache` and never served a real GraphQL endpoint — those services were kept (74 tests outside the GraphQL-specific file depend on them for non-GraphQL query-optimization/subscription bookkeeping) but no longer duplicate schema-building responsibility.
- **10 items (66 test failures) were deliberately left unbuilt after a full test-suite triage**, rather than constructed, because none of them are needed to operate the ERP for Life MDG:
  - **Mobile device auth** (`Modules/Core`, 11) — device registry/biometric-enrollment/refresh-token endpoints for the excluded Mobile/MobileSync modules; there is no React Native/Expo app anywhere in this repo to call them.
  - **FMLA eligibility checking** (`Modules/HR`, 1) — US federal employment law (12 months tenure + 1250 hours worked); has no legal meaning for a Malagasy employer, whose leave rules already come from the Code du Travail malgache/CNaPS via the kept `LeaveType`/`LeaveRequest`/`LeaveBalance` models.
  - **Offer-letter generation** (`Modules/HR`, 1) — a recruitment artefact issued before someone is an employee; ATS/recruitment was already removed from HR's "basique" scope (see above).
  - **ASC606 Revenue Recognition** (`Modules/Accounting`, 5) — see the entry above; OHADA/SYSCOHADA has no equivalent concept to port.
  - **Production-capacity forecasting** (`Modules/Analytics`, 1) — built entirely on the excluded Manufacturing module's schema (`work_centers`, `manufacturing_orders`, `bom_components`), which doesn't exist in this repo.
  - **Skill matrix / competency grid** (`Modules/HR`, 6) — the HR "basique" scope note above already documents that the training catalogue and skill-matrix visualization were removed on purpose; the routed HR skills endpoint's own code comment says so too.
  - **Agent talent management** (`Modules/Helpdesk`, 19) — coaching recommendations, SMART goals, and skill-proficiency scoring for support agents is 360°-performance-review territory wearing a Helpdesk badge; excluded for the same reason HR's own 360° reviews were.
  - **Onboarding funnel telemetry** (`Modules/Setup`, 15) — `OnboardingSession`/`OnboardingStepEvent`/`FunnelSnapshot` measure WideHalo's own product-marketing KPI (wizard completion rate, median setup minutes, AI-mapping adoption) about the onboarding wizard itself, not something a Malagasy SME needs in order to run its own onboarding.
  - **`MinioService` (Deepnest/Blender render pipeline)** (`Modules/Integration`, 2) — object storage for 3D-nesting/CAD renders, a Manufacturing/PLM-domain feature, out of scope.
  - **Pessimistic task locking for real-time collaborative editing** (`Modules/Projects`, 5) — concurrent-edit lock arbitration depends on the excluded RealTime/Discussion modules.

- **Chantier 8.3 (Inventory + Logistics) rewiring/cleanup, part 1 — RBAC holes**: `Modules/Inventory/routes/api.php` had **zero** module/role gating on every one of its ~120 endpoints — only `auth:sanctum, session.security, tenancy.user` (any authenticated user of any tenant could read/write all inventory data) — fixed by adding `module:Inventory` + `role:employee,logistics-manager,warehouse-operator,purchasing-manager,inventory-analyst,manager,admin` to all 4 top-level route groups (`employee` included deliberately — it is this app's broad "every non-delete permission across every module" role by design, confirmed via the seeder, and excluding it would have broken the pre-existing "any employee can view/create products" test coverage). `Modules/Logistics`'s `CarrierPolicy`/`ShipmentPolicy`/`DeliveryRoundPolicy` were fully written but never invoked by `CarrierController`/`ShipmentController`/`DeliveryRoundController` and never registered with the Gate — fixed with `authorize()` calls throughout plus a `LogisticsServiceProvider::registerPolicies()` (same Modules-namespaced-policies-don't-auto-discover pattern as Core/BI) and a new `LOGISTICS_EXTRA_PERMISSIONS` block (8 `logistics.deliveryround.*` strings — `deliveryround` wasn't in the generic `MODULES['logistics']` resource list). Both fixes broke pre-existing tests for two different reasons, both fixed rather than worked around: 14 Inventory test files (delegated to a background agent, verified independently after) created bare unroled `User::factory()->create()` users that the new gate now rejects — added the seed-guard + `->assignRole('employee')` pattern; 6 Logistics test files called `Role::firstOrCreate(['name' => 'logistics-manager', ...])` directly without ever running `RolesAndPermissionsSeeder`, so the role existed with zero permissions attached — worked fine against route-only gating, broke the moment `authorize()`/Policy checks were added — fixed with the same seed-guard. `Modules/Logistics/tests/Feature/Chantier83LogisticsRbacTest.php` (new, 5 tests) locks in both fixes: a plain `sales-rep` (zero logistics permissions by design — it only gets `crm.*`) is denied creating a carrier/delivery round and deleting a shipment; `logistics-manager` can do all three.
- **Chantier 8.3 (Inventory + Logistics) rewiring/cleanup, part 2 — active breakage**: `/categories`, `/warehouses`, and `/stock-adjustments` 500'd on every visit under their `create`/`show`/`edit` actions (and `/stock-adjustments` on `index` too) — `Modules/Inventory/app/Http/Controllers/Web/{Category,Warehouse,StockAdjustment}Controller.php` rendered `Categories/{Form,Show}.vue`, `Warehouses/{Form,Show}.vue`, and `StockAdjustments/{Index,Form,Show}.vue`, none of which existed anywhere in the repo. `stock-adjustments` was deleted outright rather than built: `Stock/Movements.vue` (already real, already routed at `/stock/movements`) already covers manual stock adjustments end-to-end via `POST stock-movements` with `type: 'adjustment'` against the real `StockMovement` model — the separate resource was 100% redundant scaffolding with no API route behind it at all. `categories`/`warehouses` were real, reachable CRUD APIs with no working page — built `Categories/Index.vue` as a new self-contained list+modal-CRUD page on the exact pattern already used (and already working) by `Warehouses/Index.vue`, then trimmed both Web controllers down to their one real `index()` action, since the modal-based pages call the JSON API directly and never needed the separate create/store/show/edit/update/destroy web routes. Found and fixed two adjacent bugs while building this: `Warehouses/Index.vue` read `data.current_page`/`data.total`/`data.last_page` directly from the paginated API response instead of `data.meta.*` (`WarehouseResource::collection()` on a paginator wraps pagination info under `meta`, Laravel's default) — the page listed correctly but its pager silently never rendered; `CategoryResource`/`Store`/`UpdateCategoryRequest` referenced a `status` field that was never migrated onto `inventory_categories` at all — harmless (nullable, always resolved to `null`) but removed to match the real schema.
- **Chantier 8.3 (Inventory + Logistics) rewiring/cleanup, part 3 — stub-table columns**: the catch-all scaffold migration left 26 `inventory_*` and 12 `logistics_*` tables as bare `id/tenant_id/status/data/timestamps` stubs; most were patched to match their models by earlier passes, but a full model/controller cross-check (`Schema::getColumnListing()` vs each model's `$fillable`, run against a fresh migration) found 11 tables still missing columns their own already-routed controllers actively write — a genuine `QueryException` on every real request, not a hypothetical gap: `inventory_cycle_counts.assigned_to` (`CycleCountController::store`), `inventory_picking_orders.source_id` (`PickingOrderController::store`), `inventory_purchase_orders.expected_at`/`received_at` (`PurchaseOrderController::store`/`receive`), `logistics_carriers.{website,tracking_url_template,api_provider,api_credentials,notes}` and `logistics_carrier_rates.{origin_zone,destination_zone,valid_from,valid_until}` (`CarrierController`/`CarrierRateController`), `logistics_routes`' full geographic field set (`RouteController`), `logistics_shipments.{origin_warehouse_id,destination_warehouse_id,value_currency,estimated_cost,actual_cost,booked_at,picked_up_at,temperature_min,temperature_max,co2_kg}` (`ShipmentService`/`LogisticsAnalyticsService`'s `co2_kg` query), and 4 fully-bare Logistics stubs behind real, routed, real-model controllers (`logistics_freight_invoices`, `logistics_putaway_rules`, `logistics_shipment_lines`, `logistics_shipment_packages`). Two additive patch migrations (`Modules/Inventory/.../2026_08_27_000001_patch_inventory_stub_table_columns.php`, `Modules/Logistics/.../2026_08_27_000001_patch_logistics_stub_table_columns.php`) close all of them, matched field-for-field against real usage rather than guessed from the models alone — `PutawayRuleController` turned out to bypass the `PutawayRule` Eloquent model entirely and write via raw `DB::table()` with a completely different field set (`product_category`/`carrier_id`/`transport_mode`/`requires_cold_chain`/`has_hazmat` vs the model's unused `product_category_id`/`strategy`/`temperature_required`) — the migration matches the controller's real, validated fields, not the model's dead ones. `Lot.created_by`/`LotMovement.created_by`/`PoReceiptLine`'s full field set/`ReorderRule`'s full field set were patched too even though currently orphaned (no controller reaches them yet — `PoReceiptLine`/`ReorderRule` in particular have zero routes), on the same "close the landmine before the next chantier trips it" precedent as the Chantier 8.2 (Helpdesk) 8-model migration. A second, deeper bug surfaced while writing the regression test for shipment lifecycle transitions: `ShipmentController::book()`/`dispatch()`/`deliver()`/`cancel()` had `ShipmentService` injected but never called it — they set `status` directly instead, so `booked_at`/`picked_up_at`/the shipment's tracking-event trail were silently never written even after the schema fix, and `dispatch()`'s hardcoded `status: 'dispatched'` was actually the wrong vocabulary for this model (`'dispatched'` belongs to the separate, unrelated `LgxShipment` — this module's real `ShipmentFactory`/`TrackingEventController`/`TrackingEventFactory` all use `'picked_up'`). Fixed by delegating all four methods to the already-written, already-correct `ShipmentService` methods.
- **Chantier 8.3 (Core + Security) rewiring/cleanup**: a full API/Controller/View/Data audit found the deepest set of RBAC holes of any chantier so far — several endpoints had *zero* authorization of any kind, not just a missing seed. `ServiceIdentityController`/`TrustZoneController`/`RateLimitController`/`AuthenticationEventController` had no `authorize()` calls, no `company_id` scoping, and (for the first two) no Policy class at all — any authenticated user of any tenant could list/rotate service-to-service credentials (`client_secret`/private-key material returned in the response), block/unblock arbitrary IPs, and read every tenant's login/failure history. `ComplianceControlController`/`ThreatIndicatorController` also had zero `authorize()` calls despite `ComplianceControlPolicy`/`ThreatIndicatorPolicy` already existing and being correctly used by sibling controllers for the same models. Fixed: added `ServiceIdentityPolicy`/`TrustZonePolicy`/`ComplianceViolationPolicy` (new — the first two required a rewrite of their controllers too, since both validated/wrote field names — `name`/`client_id`/`client_secret`/`trust_level`/`ip_ranges` — that matched neither the real migrated table nor even `TrustZone`'s own already-correct `$fillable`; `2026_08_26_000001_patch_security_trust_zones_and_service_identities.php` adds the missing `zone_type`/`cidr_blocks`/`device_policies`/`authentication_policies`/`trust_score_minimum`/`assigned_resources` columns `security_trust_zones` needed to match its model), `authorize()` calls added throughout `ComplianceController` (`storeControl`, the 3 `*Violation` methods) and `EncryptionController::storeEncryptedField`; `ComplianceControlController` (100% redundant with the real, working `ComplianceController::*Control` methods — confirmed via frontend grep, the live `Index.vue` dashboard calls `compliance/controls` not `compliance-controls`) was deleted outright rather than fixed, matching the CRM `TerritoryManagementController` precedent; `ThreatIndicatorController` was kept (the live dashboard does call it) but had a real bug fixed alongside the RBAC hole — it validated/filtered on a `severity` column that doesn't exist on `security_threat_indicators` (real column is `threat_level`), so `severitySummary()` was an unconditional SQL error on every call. `RateLimitController`/`AuthenticationEventController` have no natural model to hang a Policy off (cache-backed / no `company_id` on the model at all), so both were gated by `role:security-admin,admin,super-admin` route middleware instead, the same pattern already used for `TerritoryController` in Chantier 8.2. **A deeper, repo-wide bug surfaced while testing the new policies**: every Security-module `company_id` column is `string(36)` (`2026_08_16_000001_fix_security_compliance_violations_table.php`'s own comment confirms this was deliberate, "matching every sibling Security model's company_id column" — a leftover from an original UUID-tenant design) while `users.company_id` is `unsignedBigInteger` — so the `$user->company_id === $model->company_id` ownership check used by **every** Security policy (`ComplianceAuditPolicy`, `ComplianceControlPolicy`, `ComplianceViolationPolicy`, `EncryptedFieldPolicy`, `EncryptionKeyPolicy`, `SecurityIncidentPolicy`, `ServiceIdentityPolicy`, `TrustZonePolicy` — 8 files, 28 comparisons) was comparing an int to a string and silently always failing. Not a security hole (fails closed, denies everyone including legitimate `security-admin` users) but a real correctness bug that would have surfaced the moment anyone actually tried to use these features — fixed by casting both sides to string at every comparison site. On the Core side: `ApprovalController`/`CustomFieldController` had `ApprovalWorkflowPolicy`/`CustomFieldPolicy` fully written and already referenced via `$this->authorize()` calls that were silently never added (they weren't — this chantier added them) and, separately, neither policy was ever registered with Laravel's Gate (`CoreServiceProvider::registerPolicies()`, new, mirroring the BI/Helpdesk precedent) since Modules-namespaced policies don't auto-discover the way `App\Policies` ones do; `CORE_EXTRA_PERMISSIONS` (new, `RolesAndPermissionsSeeder`) seeds the 16 `core.{approvalworkflow,customfield}.*` permission strings, since `core` wasn't in the generic `MODULES` list at all. `SuperadminController` (Phase 40's full multi-tenant portal — provision/suspend/reactivate/upgrade-plan/purge/export, global stats, audit log, onboarding) and `SmartDefaultsController` were both fully written, matching their own docblocked routes exactly, but neither had ever been registered in `routes/api.php` — wired up now, split into `superadmin/*` (role:super-admin), `onboarding/*` (tenant-scoped per the controller's own "not superadmin" section comment), and `core/{smart-defaults,defaults}` groups. `CspViolation`/`CspViolationLogger`/`CspViolationPolicy` were fully written and tested (from an earlier chantier) but had no controller/route anywhere — browsers had nowhere to actually POST their CSP `report-uri` violations to; added `CspViolationController` (public/unauthenticated `POST core/csp/report`, IP-throttled via the existing `webhook` limiter, plus authenticated `index`/`show`/`resolve`/`stats`) and fixed `CspViolationPolicy`'s role checks, which referenced `security_manager`/`compliance_officer` roles that don't exist in this repo's seeder (real names are `admin`/`security-admin`). Cleanup: deleted `Modules\Core\Http\Controllers\Api\GDPRController` (100% duplicate of the real, routed `GdprController` — same class name differing only by case, a PSR-4 landmine on case-sensitive filesystems), `Modules\Security\Http\Controllers\GdprDataExportController` (orphaned, superseded by Core's `GdprController`, and non-functional on its own since its `gdpr_export_requests`/`gdpr_deletion_requests` tables were never migrated), and the dead `CoreController` scaffold + its incomplete blade views (only `index.blade.php` existed; `create`/`show`/`edit` routes would have 500'd).
