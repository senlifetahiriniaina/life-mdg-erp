# AI

## Rôle

`Modules/AI` porte le principe « AI Assisted First » de life-mdg-erp : il fournit le service central `AiContextualAssistantService::getGuidance()` que tous les autres modules interrogent (via le seul vrai endpoint `POST /api/v1/ai/assist`, appelé par le composable frontend `useAiAssistant()`) pour afficher une aide contextuelle générée par Claude sur chaque écran/action, avec un repli statique (`fallback`) garanti quand la clé API Anthropic est absente ou que l'appel échoue. Il expose en complément des briques IA plus spécialisées : détection d'anomalies (calculées en direct sur les vraies tables métier, pas persistées), recherche en langage naturel, conseiller d'actions et suivi budgétaire des appels IA (coût, tokens, quotas). L'AI module n'importe aucun autre module métier — c'est la dépendance racine du graphe applicatif (seule dépendance : `Modules\Core\Services\AI\AIService`).

## Modèles clés

| Modèle | Table DB | Rôle |
|---|---|---|
| `AiUsageLimit` | `ai_usage_limits` | Quotas d'usage IA par tenant/utilisateur (`limit_type`, `limit_value`, `period`, `block_on_exceed`) — utilise le trait `HasAuditLog` du module AuditLog |

`AiInsight`/`AiRequest` avaient déjà été supprimés lors d'une session antérieure (zéro consommateur réel). **Chantier 32.2 (audit approfondi en 14 couches) a supprimé les deux modèles restants qui portaient le même défaut** : `AiAnomaly`/`ai_anomalies` et `AiRecommendation`/`ai_recommendations` — deux tables réellement migrées, avec un modèle Eloquent réel chacune, mais confirmées (grep exhaustif sur tout le dépôt) sans aucun lecteur ni écrivain nulle part. La détection d'anomalies réelle (`AiAnomalyDetectionService::getActiveAnomalies()`) calcule tout à la volée sur les vraies tables métier et stocke le résultat dans le cache de réponse (`Cache::remember`), sans jamais toucher le modèle `AiAnomaly` — un design volontaire, pas un oubli de câblage. De même, `Modules\Strategy\Services\StrategyAIService::recommend()` (la seule vraie fonctionnalité « recommandations IA » de l'app) est entièrement sans état, elle ne persiste jamais dans `AiRecommendation`.

**Le suivi réel de l'usage IA (`ai_usage_logs`) avait une table manquante, jamais migrée nulle part dans le dépôt** — confirmé par une vraie requête HTTP contre `GET /api/v1/ai/usage/me`, qui renvoyait un 500 `SQLSTATE... no such table: ai_usage_logs` sur chaque appel réel, pour chaque utilisateur, sans condition. La table sœur `ai_usage_limits` avait bien été migrée (`database/migrations/2026_09_01_000001_...`), ce qui explique pourquoi ce trou a survécu à 3 passes d'audit antérieures portant sur ce même fichier (Chantier 8.5-light, Chantier 10, Chantier 19 Lot 3) sans jamais être détecté — aucune n'avait exécuté une vraie requête contre `myUsage()`/`adminUsage()`. Corrigé par une nouvelle migration (`Modules/AI/database/migrations/2026_10_10_000001_create_ai_usage_logs_table.php`), colonnes alignées exactement sur ce que `AiUsageBudgetService::logUsage()`/`getUsage()`/`getAdminSummary()` écrivent/lisent réellement.

## Endpoints principaux

Tous préfixés `/api/v1/ai/`, protégés `auth:sanctum` + **`module:AI`** (gate ajoutée au Chantier 32.2 — voir Particularités) :

- **Assistant contextuel (AI Assisted First)** : `POST assist`, `GET assist/modules` — implémentés par `AiAssistantController`, qui délègue directement à `AiContextualAssistantService`
- **Anomalies** : `POST anomalies/detect`, `GET anomalies`, `DELETE anomalies/{id}`
- **Recherche en langage naturel** : `POST search`
- **Conseiller d'actions** : `POST advise`, `GET usage/me`
- **Administration budget IA** (`/api/v1/ai/admin/`, `hasAnyRole(['admin','super-admin'])`) : `GET usage`, `GET limits`, `POST limits`, `DELETE limits/{id}`

`analytics/*`, `recommendations/*`, `nlp/*`, `insights/*` — les ~25 routes qui auraient exposé `PredictiveAnalyticsService`/`RecommendationEngineService`/`NaturalLanguageProcessingService`/`AutomatedInsightsService` (voir Services) — n'ont jamais été enregistrées (les 4 classes de contrôleur ciblées n'ont jamais existé). Depuis le Chantier 32.2, ce n'est plus documenté comme du backlog de fonctionnalité : les 4 services eux-mêmes ont été supprimés (voir Services), donc il n'y a plus rien à router ici.

## Contrôleurs

`Modules/AI/app/Http/Controllers/Api/` (4 fichiers, tous les contrôleurs réellement routés du module) :

| Contrôleur | Rôle |
|---|---|
| `AiAssistantController` | Assistant contextuel — délègue à `AiContextualAssistantService`. C'est le **seul** point d'entrée HTTP réellement appelé par le frontend : confirmé par un grep exhaustif de tous les appels `useAiAssistant()`, qui postent tous vers `/api/v1/ai/assist`, jamais vers l'un des 26 contrôleurs `<Module>AiAssistController` que possède chaque autre module (`Modules/Accounting/.../AccountingAiAssistController`, etc.) — chacun d'eux délègue lui aussi correctement à `AiContextualAssistantService::getGuidance()`, mais aucun n'est appelé par une seule page Vue réelle du dépôt. Ce sont donc 26 chemins HTTP redondants et morts dans 26 *autres* modules, hors périmètre de ce module — signalé pour un futur chantier ciblé, pas corrigé ici. |
| `AiAnomalyController` | Détection/liste/rejet d'anomalies, scopé `company_id` |
| `AiSearchController` | Recherche en langage naturel, scopée `company_id` |
| `AiActionAdvisorController` | Conseiller d'actions + administration du budget IA (`requireAdmin()`) |

## Vues (Vue/Inertia)

Aucune route web n'existe pour ce module (`Modules/AI/routes/web.php` absent) — conforme au principe « API First » : le module n'a pas d'interface propre, son unique point de contact frontend est le composable `useAiAssistant` consommé par les autres modules. `AiActionAdvisor.vue` (`Modules/AI/resources/js/Components/`) est un composant réel et complet — un dialogue « pré-action » qui appelle le vrai `POST /api/v1/ai/advise` et affiche risques/alternatives/conséquences avant une action risquée — mais reste **délibérément non monté** : le décider nécessiterait de modifier des pages dans d'autres modules (où déclencher l'avertissement — suppression, clôture de session POS, envoi de campagne…), une décision produit hors du périmètre de ce module. `Agents/Index.vue` (« Agents IA Autonomes », 100 % mock) avait déjà été supprimée lors d'une session antérieure (Chantier 9).

## Services

- `AiContextualAssistantService` — service central du principe AI Assisted First. `getGuidance(module, action, context, locale, userRole)` retourne un JSON structuré (`what_to_do`, `how_to_do`, `decision_indicators`, `warnings`, `next_actions`, `tips`). Ne parle plus directement à `api.anthropic.com` : elle délègue à `Modules\Core\Services\AI\AIService::forModule('AI')->chat(...)`, qui résout le provider actif (`AI_DEFAULT_PROVIDER`, ou un override `module_providers.AI` — voir `docs/03-MODULES/Core.md`). `$enabled` reflète `isConfigured()` du provider effectivement résolu (pas seulement `ANTHROPIC_API_KEY`) : avec le provider par défaut `anthropic`, c'est équivalent au comportement historique ; avec `AI_DEFAULT_PROVIDER=deepseek`, `enabled` reflète la présence de `DEEPSEEK_BASE_URL`. Toute exception levée par `chat()` (provider injoignable, erreur HTTP) est absorbée et retombe sur `fallbackGuidance()` — `getGuidance()` ne lève jamais d'exception, quel que soit le provider actif. `supportedModules()` liste tous les couples module/action couverts par le fallback statique — la carte couvre bien plus large que les 27 modules du périmètre life-mdg-erp (POS, Manufacturing, Ecommerce, Quality, PLM, Contracts, Assets, MarketingAutomation, etc. y figurent encore alors que ces modules ont été retirés) ; voir Particularités pour les 3 modules réels ajoutés au Chantier 32.2.
- `AiActionAdvisorService` / `AiUsageBudgetService` — conseille des actions et calcule l'usage/coût IA par période (`daily/weekly/monthly`), avec tarification codée en dur (`claude-sonnet-4-6` : 3 $/M tokens input, 15 $/M output). `AiUsageBudgetService` lit/écrit désormais une vraie table `ai_usage_logs` (voir Modèles clés) — auparavant garanti fatal sur toute lecture réelle.
- `AiAnomalyDetectionService` — détection d'anomalies exposée via `AiAnomalyController`. Interroge les vraies tables préfixées par module (`acc_*`, `crm_*`, `inventory_*`, etc.), résultat gardé en cache, jamais persisté dans un modèle Eloquent (voir Modèles clés).
- `AiNaturalLanguageSearchService` — recherche en langage naturel exposée via `AiSearchController` ; le filtre tenant ne fait confiance qu'à une vraie colonne `tenant_id` (vérifiée via `Schema::hasColumn()`), jamais à `company_id` — `crm_contacts.company_id` est une FK vers une société *cliente* CRM, pas la frontière tenant de l'application, une collision de nom à ne pas reproduire.
- **Supprimés au Chantier 32.2 (audit approfondi en 14 couches, couche 9 « fake/dead »)** : `PredictiveAnalyticsService`, `RecommendationEngineService`, `NaturalLanguageProcessingService`, `AutomatedInsightsService`, `AnthropicCacheService`. Confirmés sans aucun appelant réel nulle part dans le dépôt (uniquement `new X()` dans leurs propres tests, jamais via le conteneur). Chacun était soit du code de démonstration 100 % factice (`uniqid()`/`rand()` pour des scores inventés, un appel `Cache::getRedis()->keys()` garanti fatal sur le driver de cache réel `file` de cette app), soit un doublon fonctionnel d'une implémentation réelle et déjà utilisée ailleurs : modèles prédictifs → le vrai `ForecastingEngineService` d'Analytics et le vrai `PredictiveAnalyticsService`, testé, de BI (même nom de classe, namespace différent) ; détection d'anomalies → le vrai `AiAnomalyDetectionService` de ce module lui-même ; cache de réponse IA → le `Cache::remember()` déjà intégré dans `AiContextualAssistantService`. Le domaine même de `RecommendationEngineService` (un recommandeur de produits e-commerce générique, catalogue codé en dur `'electronics'/'software'/'services'`) est en plus doublement hors périmètre : Ecommerce ne fait pas partie des 27 modules de Life MDG.

## Permissions RBAC

Le module AI n'a pas de bloc `ai.*.*` dans `RolesAndPermissionsSeeder::MODULES` — aucune permission Spatie granulaire n'est seedée pour lui. Le contrôle d'accès repose sur `auth:sanctum` + **`module:AI`** (gate ajoutée au Chantier 32.2 — voir Particularités) au niveau des routes, sur `AiActionAdvisorController::requireAdmin()` (vérifie `hasAnyRole(['admin','super-admin'])`), et sur le scope `company_id` appliqué par `AiAnomalyController`/`AiSearchController`.

## Dépendances avec d'autres modules

- **Utilisé par** : `AiContextualAssistantService` est importé par de nombreux fichiers hors du module AI, dans quasiment tous les modules métier (CRM, Accounting, HR, Inventory, BI, Helpdesk, Projects…) sous forme de services `<Module>AIService` dédiés qui l'enveloppent (ex. `Modules\CRM\Services\AI\CrmAIService`, `Modules\Accounting\Services\AI\AccountingAIService`, `Modules\HR\Services\AI\HrAIService`), et surtout via le composable frontend `useAiAssistant()`, réellement consommé par des dizaines de pages Vue à travers tout le dépôt.
- **Utilise** : `Modules\Core\Services\AI\AIService` (voir `docs/03-MODULES/Core.md`) pour exécuter réellement l'appel au provider IA actif — c'est la seule dépendance du module AI vers un autre module. Aucun autre module métier n'est importé.

## Provider auto-hébergé (DeepSeek)

En plus d'Anthropic/OpenAI, un provider DeepSeek auto-hébergé (servi via Ollama, voir `docker-compose.deepseek.yml`) est disponible pour ce module au même titre que pour `AIService` en général. Comportement par défaut inchangé (`AI_DEFAULT_PROVIDER=anthropic`) ; activation via `AI_DEFAULT_PROVIDER=deepseek` ou un override `module_providers.AI` dans `config/ai.php`. Détails de mise en place : `docs/07-DEPLOIEMENT/IA-AUTOHEBERGEE.md`.

## Particularités du périmètre life-mdg-erp

- **Faille cross-tenant corrigée (session antérieure)** : `AiAnomalyController`/`AiSearchController::resolveTenantId()` faisait `isset($user->tenant_id) ? ... : (int) $request->header('X-Tenant-Id', 1)` — corrigé sur `$user->company_id ?? 0`, le repli par en-tête entièrement supprimé.
- **`module:AI` ajouté au Chantier 32.2** : contrairement à chaque module métier de l'app, qui gate ses routes sur `module:<Nom>` (pour qu'un admin de tenant puisse le désactiver via la vraie table `tenant_modules`), ce module n'avait jamais eu ce gate du tout — n'importe quel utilisateur authentifié pouvait toujours atteindre `/api/v1/ai/*`, même pour un tenant ayant explicitement désactivé le module 'AI'. Corrigé pour la cohérence avec le reste de l'app ; le composable frontend `useAiAssistant` dégradait déjà proprement sur tout échec HTTP (y compris un 403), donc ce correctif ne nécessite aucun changement frontend.
- **`supportedModules()` avait un vrai trou trouvé et corrigé au Chantier 32.2, le même motif que le Chantier 30 sur Strategy** : un grep systématique de tous les appels réels `useAiAssistant(module, action)` à travers tout le dépôt (racine `resources/js` + chaque `Modules/*/resources/js`) a trouvé 3 modules entiers appelés depuis une vraie page montée mais jamais enregistrés (`Analytics.view_dashboard`, `Integration.view_dashboard`, `Security.view_dashboard`), plus 4 actions manquantes sur 2 modules déjà enregistrés (`Helpdesk.view_dashboard`, `Calendar.calendar_integrations`/`team_calendar`/`view_event`) — chaque appel manquant se résolvait silencieusement vers un panneau d'aide vide (`enabled:false`, tous les champs vides) plutôt qu'un vrai texte. Les 7 couples ont désormais un vrai texte de repli fr+en. `supportedModules()` reste sur-large (POS, Manufacturing, Ecommerce, Quality, PLM, Contracts, Assets, Documents, MarketingAutomation, CustomerService, Notes, SmartTable… hors périmètre Life MDG) — non bloquant, un appel `getGuidance('POS', 'open_session')` renvoie simplement un texte de repli qui ne sera jamais affiché puisque le module POS n'existe pas côté frontend.
- **`AiUsageLimitFactory` était un factory de scaffold cassé** — `fake()->word()` sur chaque colonne FK/décimale/booléenne, plus une douzaine de colonnes fantômes (`name`, `title`, `slug`, `status`, `email`, `amount`…) qui n'existent pas du tout sur `ai_usage_limits` — confirmé garanti fatal sur chaque appel réel avant correctif (« no such column: name »). Corrigé pour correspondre au vrai `$fillable` et aux vraies valeurs d'énumération validées par `AiActionAdvisorController::adminSetLimit()`.
- **Trouvaille sévère, en dehors du périmètre de ce module, documentée pour un futur chantier dédié** : `php artisan config:cache` s'exécute dans le `Dockerfile` racine **au moment du build de l'image**, avant tout accès à un vrai `.env` (`.dockerignore` exclut `.env`/`.env.*`) — le fichier de config figé (`bootstrap/cache/config.php`) est ensuite copié tel quel dans le conteneur d'exécution final, et rien dans `docker-compose.prod.yml` ne relance `config:cache` au démarrage avec les vraies variables d'environnement injectées à ce moment-là. Concrètement, `config('ai.providers.anthropic.api_key')` — la lecture canonique que `AiContextualAssistantService` utilise via `AIService` — resterait figée sur la valeur (vide) présente au moment du build, **quelle que soit la vraie clé Anthropic configurée à l'exécution** en production. Ce n'est pas un bug de `Modules/AI` lui-même (le code applicatif suit exactement le bon patron Laravel) mais un défaut de configuration Docker/déploiement qui, s'il est confirmé en conditions réelles, désactiverait silencieusement « AI Assisted First » (l'un des 7 principes fondateurs) dans toute l'application déployée. Hors périmètre de correction ici (touche `Dockerfile`/`docker-compose.prod.yml`, pas `Modules/AI`) — signalé avec la sévérité qu'il mérite pour un futur chantier dédié à l'infrastructure de déploiement.
