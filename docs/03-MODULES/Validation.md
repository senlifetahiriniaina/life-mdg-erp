# Validation

## Rôle

`Validation` est le moteur d'approbation générique de life-mdg-erp : il ne connaît aucune entité métier directement, mais expose un workflow d'approbation réutilisable (règles, hiérarchies, historique) que n'importe quel autre module peut brancher sur ses propres modèles via une relation polymorphe (`approvable_type` / `approvable_id`). Dans ce périmètre, il est concrètement utilisé par `Achats` pour le routage d'approbation des commandes fournisseur (`PurchaseOrder`).

## Modèles clés

| Modèle | Table DB | Rôle |
|---|---|---|
| `ApprovalWorkflow` | `validation_approval_workflows` | Un workflow nommé, rattaché à un `module_name` (ex. `Achats`), actif ou non. |
| `ApprovalRule` | `validation_approval_rules` | Règle conditionnelle d'un workflow (ex. condition sur montant, fournisseur, catégorie fournisseur). |
| `ApprovalRequest` | `validation_approval_requests` | Demande d'approbation concrète : relation polymorphe `approvable()` vers l'entité métier (ex. un `PurchaseOrder`), statut, demandeur, approbateur. |
| `ApprovalAction` | `validation_approval_actions` | Action effectuée sur une requête (approuver, rejeter, déléguer) avec commentaire. |
| `ApprovalHistory` | `validation_approval_histories` | Historique chronologique des changements d'état d'une requête. |
| `ApprovalHierarchy` | `validation_approval_hierarchies` | Hiérarchie d'approbation nommée, éventuellement rattachée à une `company_id`. |
| `HierarchyLevel` | `validation_hierarchy_levels` | Niveau ordonné (`level_order`) au sein d'une hiérarchie, avec titre et nombre d'approbateurs requis. |
| `LevelApprover` | `validation_level_approvers` | Utilisateur assigné à un niveau, avec ordre et approbateur de secours (`backup_user_id`). |

Tous les modèles principaux utilisent `SoftDeletes` et le trait `Modules\Core\Traits\RecordsActivity` (`$auditModule = 'Validation'`).

## Endpoints principaux

Routes API sans préfixe de module dans `routes/api.php` (`throttle:simple_get` en lecture, `throttle:create_post` en écriture) :

| Méthode | Route | Description |
|---|---|---|
| GET | `approval-workflows` / `{workflow}` | Liste / détail des workflows |
| GET | `approval-workflows/{workflow}/rules` / `{rule}` | Règles d'un workflow |
| POST/PUT/DELETE | `approval-workflows`, `approval-workflows/{workflow}` | CRUD workflow |
| POST/PUT/DELETE | `approval-workflows/{workflow}/rules...` | CRUD règles |
| GET | `approval-requests` / `{request}` / `{request}/history` | Liste, détail et historique des demandes |
| POST | `approval-requests` | Créer une demande d'approbation |
| POST | `approval-requests/{approval_request}/approve` \| `/reject` | Approuver / rejeter |
| POST | `approval-requests/{request}/delegate` | Déléguer une approbation |
| GET | `approval-hierarchies` / `{hierarchy}` | Liste / détail des hiérarchies |
| POST/PUT/DELETE | `approval-hierarchies...` | CRUD hiérarchie |
| POST | `approval-hierarchies/{hierarchy}/levels` | Ajouter un niveau |
| POST | `approval-hierarchies/{hierarchy}/levels/{level}/approvers` | Ajouter des approbateurs à un niveau |
| POST | `ai/assist` (`prefix: v1/validation`) | Guidance IA contextuelle |
| GET/POST | `validation-rules`, `validation-rule-sets`, `validation-rule-sets/{ruleSet}`, `validation-rule-sets/{ruleSet}/validate` | Moteur de règles de données génériques — endpoint sœur, distinct du moteur d'approbation ci-dessus (`Modules/Validation/routes/validation-rules.php`) ; `store`/`update`/`destroy`/`addDependency`/la création de rule-set sont sous `role:admin,super-admin` (trou RBAC corrigé cette session, voir RBAC) |
| POST | `validation-rules/{rule}/dependencies`, `validation-rule-sets/{ruleSet}/rules` | Ajouter une dépendance entre règles (rejet 422 si cycle détecté) / ajouter une règle à un ensemble — nouveaux endpoints cette session, câblant `ValidationEngine::createRuleSet()`/`hasCircularDependency()`, réels et testés depuis longtemps mais jamais exposés |
| POST | `approval-workflows/{workflow}/clone` | Cloner un workflow avec ses règles — nouvellement routé cette session (méthode réelle, corrigée, jamais routée avant) |

Des routes courtes de compatibilité existent aussi (`workflows`, `requests`, `requests/{approval_request}/approve`...). Le module expose en plus 6 pages web Inertia (`routes/web.php`, `auth`) : `GET /approval-requests`, `/approval-requests/{request}`, `/workflows`, `/workflows/builder`, `/workflows/{workflow}/builder`, `/validation-rules`.

## Services

- **`ApprovalWorkflowService`** — CRUD des workflows et de leurs règles, résolution du workflow applicable à un module+type d'entité (`getApplicableWorkflow`), clonage d'un workflow avec ses règles (`cloneWorkflow`, **bug corrigé cette session** — voir Particularités).
- **`ApprovalRequestService`** — crée une `ApprovalRequest` pour n'importe quel modèle passé en argument (`createApprovalRequest($approvable, $workflow, $requestedBy)`), gère l'approbation/rejet/délégation et déclenche les événements (`ApprovalRequestCreated`, `ApprovalApproved`, `ApprovalRejected`, `ApprovalCompleted`). `getPendingApprovalsForUser()` **corrigé cette session** — voir Particularités (fuite de visibilité).
- **`ApprovalHierarchyService`** — CRUD des hiérarchies, ajout de niveaux et d'approbateurs, résolution de la chaîne d'approbateurs pour un niveau donné (`getApproverChain`).
- **`ValidationEngine`** — moteur de règles de validation de données génériques ; ses méthodes de regroupement en ensembles (`createRuleSet()`, `validateWithRuleSet()`, `hasCircularDependency()`) étaient réelles et testées mais sans contrôleur/route jusqu'à cette session — désormais exposées par `ValidationRuleSetController`.

## Permissions RBAC

Aucune entrée dédiée `validation.*` dans `RolesAndPermissionsSeeder::MODULES` — le module n'a pas de permissions Spatie granulaires. L'autorisation du moteur d'approbation passe par `ApprovalRequestPolicy`, basée sur les **rôles** plutôt que sur des permissions nommées : `viewAny` exige `admin`, `manager` ou `approver` ; `create`/`approve`/`reject`/`delegate` exigent que l'utilisateur soit l'approbateur assigné (`approver_id`) ou ait le rôle `admin`/`manager` **et appartienne à la même société que la demande** (`sameCompany()`, Chantier 31), et uniquement si la requête est encore `pending`. Le moteur de règles de données génériques (`validation-rules*`) est gaté séparément par middleware de route. Toutes les routes (`routes/api.php`, `routes/validation-rules.php`, `routes/web.php`) portent désormais le gate `module:Validation` (Chantier 32.7 — précédemment absent, le seul module du périmètre à en manquer entièrement).

Corrections RBAC / cloisonnement multi-tenant :
- **Chantier 8.5sv** : `validation-rules.php` (`store`/`update`/`destroy`/`store` d'ensembles) n'avait **aucun** gate de rôle — corrigé avec `role:admin,super-admin`. `ApprovalRequestController::index()`/`show()` n'appelaient jamais `authorize()` — corrigé.
- **Chantier 19 Lot 3** : un bug de correspondance nom-de-paramètre-de-route (`{workflow}`/`{request}`/`{hierarchy}` vs les vrais noms type-hintés `$approval_workflow`/`$approval_request`/`$approval_hierarchy`) faisait résoudre silencieusement Laravel vers un modèle vide non sauvegardé au lieu du vrai enregistrement — corrigé sur `ApprovalWorkflowController`, `ApprovalRequestController`, `ApprovalHierarchyController`.
- **Chantier 31 (headline)** : `validation_approval_requests` n'avait **aucun** cloisonnement société — un admin/manager de n'importe quelle société pouvait lister/consulter/approuver/rejeter les demandes d'approbation de n'importe quelle autre société. Corrigé avec un vrai `company_id` (peuplé depuis le demandeur réel, jamais côté client), `ApprovalRequestPolicy::sameCompany()`, et un filtre explicite dans `index()`. `ApprovalHierarchyController` avait le même trou sur `validation_approval_hierarchies.company_id` (colonne réelle, jamais vérifiée) — corrigé avec `assertVisible()` (NULL = hiérarchie globale/partagée, délibéré).
- **Chantier 32.7** : `ApprovalRequestController::store()` validait `approvable_type` contre `array_keys(Relation::morphMap())` — la map globale de **toute** l'application (8 alias, dont 6 enregistrés par `Helpdesk`), pas les 2 seuls alias que ce module enregistre lui-même (`invoice`, `purchase_order`) — corrigé avec un allowlist local. `store()` n'avait par ailleurs **aucune** vérification de propriété sur l'`approvable` résolu (IDOR confirmé empiriquement : un admin pouvait rattacher une demande à un `PurchaseOrder` d'une autre société) — corrigé (duck-typé sur la colonne `company_id`, quand elle existe). `delegate()` réassignait `approver_id` à n'importe quel utilisateur nommé dans le corps de la requête, sans aucune vérification d'appartenance à la société de la demande — corrigé.

## Dépendances avec d'autres modules

- **`Achats` → `Validation`** (dépendance dure, confirmée dans le code) : `Modules/Achats/app/Models/PurchaseOrder.php`, `Modules/Achats/app/Services/PurchaseOrderService.php`, `Modules/Achats/app/Services/ApprovalRoutingService.php` et `AchatsServiceProvider` importent `Modules\Validation\Models\ApprovalRule` et `ApprovalWorkflow`. `ApprovalRoutingService::getApplicableWorkflow()` interroge les `ApprovalWorkflow` où `module_name = 'Achats'` et évalue chaque `ApprovalRule` (condition sur montant, fournisseur, catégorie fournisseur) pour router une commande vers le bon workflow. `ApprovalRoutingService::createDefaultWorkflows()` est désormais réellement câblée dans la chaîne de seed réelle via `Modules\Achats\Database\Seeders\AchatsDatabaseSeeder` (Chantier 31 — auparavant appelée uniquement par les tests du module Achats, donc jamais réellement peuplée sur une installation fraîche). Un sous-système parallèle et redondant côté Achats (`PurchaseApprovalChainService`/`PurchaseOrderApproval`/`PurchaseApprovalController`, seuils codés en dur) a été supprimé (Chantier 8.5sv) — le vrai chemin d'approbation Achats reste exclusivement celui basé sur `Modules\Validation`/`ApprovalRoutingResolver`.
- **`Accounting` → `Validation`** : `InvoiceApprovalService` route l'approbation de factures à 3 paliers OHADA (100K/500K/10M XOF) à travers ce même moteur (`getOrCreateWorkflow()` — un workflow à 3 règles, une hiérarchie 1-niveau par règle, distinct du modèle multi-niveaux d'Achats), via `InvoiceApprovalController`.
- **`HR` → `Validation`** (lecture seule, indirecte) : `ApprovalRoutingResolver::isAvailable()` interroge `Modules\HR\Models\LeaveRequest::scopeApprovedAndCoveringDate()`/`Modules\HR\Models\ShiftSchedule` pour savoir si un approbateur résolu est actuellement en congé/hors horaire et doit être automatiquement remplacé par son suppléant — HR n'est *pas* lui-même un producteur de `ApprovalRequest` (les congés RH utilisent leur propre `LeaveRequestPolicy`/`HRService::approveLeave()`, un circuit entièrement séparé).
- **`PurchaseOrder::approval()` (Achats) — morph-map desync documenté, non touché par ce module** : `createApprovalRequest()` écrit `approvable_type` via `get_class($approvable)` (le FQCN brut), contournant le morph-map global (`invoice`/`purchase_order`) — la relation inverse `morphOne` par défaut d'Eloquent aurait comparé contre l'alias, jamais la vraie donnée stockée ; Achats a corrigé ce côté-là (Chantier 31) avec une relation `HasOne` explicite scopée sur `static::class`. `ApprovalRequest::approvable()` (le sens `morphTo`, côté Validation) n'a **pas** ce problème : `Relation::getMorphedModel()` traite une valeur non-alias comme un nom de classe littéral, donc la lecture fonctionne malgré l'écriture non-aliasée — confirmé lors de l'audit Chantier 32.7.
- Aucun autre module du périmètre n'importe `Modules\Validation` directement — le moteur reste générique et n'est câblé qu'à Achats/Accounting dans ce dépôt, bien qu'il soit conçu pour être réutilisable par tout autre module (relation polymorphe `approvable`).
- Utilise `Modules\Core\Traits\RecordsActivity` pour l'audit, et `Modules\Core\Services\ParticipantNotificationService::notifyProcess()` (Chantier 20, via `Modules\Validation\Listeners\NotifyApprovalParticipants`, écoutant les 4 événements réels `ApprovalRequestCreated`/`Approved`/`Rejected`/`Completed`) pour notifier en temps réel le demandeur, l'approbateur assigné, et le supérieur hiérarchique direct du demandeur — jamais une notification maison réinventée.

## Particularités du périmètre life-mdg-erp

- **`ApprovalWorkflowService::cloneWorkflow()` avait un bug réel, corrigé (Chantier 8.5sv)** : l'appel `$rule->replicate(['workflow_id' => $newWorkflow->id])` traite `replicate(array $except)` comme une liste de *noms* d'attributs à exclure, pas une map de substitution — c'était donc un no-op pour l'exclusion et le nouveau `workflow_id` n'était jamais réellement affecté, si bien que chaque règle clonée continuait silencieusement de pointer vers le workflow d'origine. Corrigé en `$rule->replicate()` suivi d'une affectation explicite `$newRule->workflow_id = $newWorkflow->id`.
- **`ApprovalRequestService::getPendingApprovalsForUser()` avait une fuite de visibilité, corrigée (Chantier 8.5sv)** : la méthode filtrait sur les demandes que l'utilisateur **n'avait pas encore traitées** au lieu des demandes où il **est l'approbateur assigné** — corrigé en filtrant directement sur `approver_id === $user->id`.
- **Chantier 32.7 (audit approfondi 14 couches) — bugs réels trouvés et corrigés** :
  - `Modules\Validation\Listeners\NotifyApprovalParticipants` construisait chaque `action_url` de notification sous la forme `/validation/approval-requests/{id}` — une URL qui n'a **jamais existé** : `RouteServiceProvider` enregistre `routes/web.php` sans aucun préfixe (contrairement au groupe API, préfixé `api/v1/validation`), donc la vraie page routée est `/approval-requests/{id}`. Chaque notification liée à une approbation avait un lien mort depuis la mise en place de ce listener (Chantier 20). Corrigé.
  - `ApprovalRuleController::store()`/`update()` ne validaient jamais `hierarchy_id`, bien que `Workflows/Builder.vue`'s sélecteur "Approver hierarchy" l'envoie systématiquement — silencieusement abandonné à chaque sauvegarde réelle de règle, si bien que `ApprovalRoutingResolver::resolveHierarchy()` retombait toujours sur la hiérarchie générique du module plutôt que sur le choix explicite de l'admin. Corrigé.
  - `ApprovalHierarchyController::store()`/`update()` n'acceptaient jamais `module_name`/`escalation_role` — deux colonnes réelles, activement lues par `ApprovalRoutingResolver` — si bien qu'une hiérarchie créée via cet endpoint (par opposition au seed direct Eloquent d'Achats) ne pouvait jamais être résolue. Corrigé.
  - `Workflows/Index.vue`'s 3 boutons « Quick Start Templates » naviguaient vers `/workflows/builder?template=...`, mais `Builder.vue` ne lisait jamais ce paramètre — les 3 modèles de démarrage rapide étaient une fonctionnalité 100% factice (cliquer ouvrait un formulaire vide). Corrigé avec 3 préréglages frontend autonomes (nom/module/règles), sans toucher le backend.
  - `ApprovalRequests/Show.vue` n'avait **aucun** wrapper `<AppLayout>` — la page de détail d'une demande d'approbation s'affichait sans navigation/barre latérale de l'application. Corrigé.
  - Le module n'avait **aucun** gate `module:Validation` sur ses routes (API, moteur de règles génériques, et web) — le seul module du périmètre dans ce cas. Corrigé (voir RBAC ci-dessus).
  - `'Validation'` n'était pas enregistré dans `AiContextualAssistantService::supportedModules()`, et aucune des 5 pages Vue réelles du module n'appelait `useAiAssistant()` — le même double-manque déjà trouvé et corrigé pour `'Strategy'` au Chantier 30. Corrigé (5 actions réelles enregistrées, texte de repli fr+en, câblage sur les 5 pages).
- **Confirmé, documenté, non corrigé (décision produit hors périmètre d'un audit)** : approuver/rejeter/déléguer via l'endpoint générique de Validation (`POST approval-requests/{id}/approve`) fait avancer/finaliser la vraie `ApprovalRequest`, mais ne synchronise **jamais** l'état de l'enregistrement métier sous-jacent (`PurchaseOrder.status`, `Invoice`...) — cette synchronisation n'existe que dans les contrôleurs spécifiques à chaque module consommateur (`PurchaseOrderService::markAsApproved()`/`markAsRejected()`, qui re-consultent l'`ApprovalRequest` et appellent une seconde fois `approveRequest()`/`rejectRequest()`). Un utilisateur passant directement par l'endpoint générique de Validation (au lieu du contrôleur métier dédié) peut donc faire avancer une chaîne d'approbation sans jamais faire progresser le statut du `PurchaseOrder`/`Invoice` correspondant — un vrai risque de désynchronisation, mais dont la correction exigerait de toucher Achats/Accounting (hors périmètre explicite de cet audit, scopé à `Modules/Validation` seul). Flagué pour un futur chantier dédié à la synchronisation cross-module.
- **Confirmé, documenté, non corrigé** : `ValidationRule`/`ValidationRuleSet`/`ValidationEngine` (le moteur générique de validation de données, distinct du moteur d'approbation) sont réels, testés, et réellement atteignables de bout en bout (page `ValidationRules/Index.vue` + les endpoints `validation-rule-sets*`) — mais **aucun autre module de l'application ne les invoque automatiquement** avant une création/modification de ses propres enregistrements ; ils ne sont utilisables que via cette page d'administration ou un appel API explicite. Ce n'est pas du code mort au sens strict (un vrai chemin d'utilisation existe et fonctionne), mais un gap d'adoption — brancher ce moteur sur les formulaires d'autres modules impliquerait de toucher ces modules, hors périmètre de cet audit.
- **Confirmé sans FK au niveau base de données** : les 10 tables de ce module (`validation_approval_*`, `validation_hierarchy_levels`, `validation_level_approvers`, `validation_rules`, `validation_rule_sets`) n'ont **aucune** contrainte de clé étrangère réelle (confirmé via `Schema::getForeignKeys()`) — chaque relation Eloquent (`workflow_id`, `hierarchy_id`, `request_id`...) n'est qu'une colonne entière ordinaire, cohérent avec l'origine catch-all-scaffold de la majorité de ces tables. Risque atténué en pratique : `ApprovalWorkflow`/`ApprovalHierarchy` (les deux seuls modèles "parents" ayant un `destroy()` réellement exposé) utilisent `SoftDeletes`, donc leur suppression ne détruit jamais physiquement les lignes enfants (règles, niveaux, approbateurs) — elles restent orphelines-mais-récupérables plutôt que perdues. Aucun endpoint de suppression physique (`forceDelete`) n'existe nulle part dans ce module.
