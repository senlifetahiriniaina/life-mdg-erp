# Payroll

## Rôle

Le module Payroll est la source unique de vérité pour la paie dans life-mdg-erp (voir `CLAUDE.md`) : cycles de paie (« runs »), bulletins de salaire, et barèmes fiscaux/sociaux par pays africain (Africa First). Il fournit aussi un service d'intégration comptable OHADA et un jeu de données statutaires réel (impôt progressif + régimes de cotisations sociales pour 8 pays) réellement branché sur le calcul de paie.

**Chantier 32.18 (audit approfondi en 14 couches)** : audit empirique complet du module (route → contrôleur → vue → modèle → format de données → sécurité approfondie → RBAC → validation métier → fake/dead → relationnel → CORE → API → IA → import/export/rapport). A trouvé et corrigé une IDOR cross-tenant réelle sur `GET payslips/{payslip}`, un bug d'affichage de devise codée en dur, un cycle de vie `PayrollRun` jamais synchronisé avec les vraies actions du contrôleur, une notification employé jamais câblée, et a supprimé un sous-système mort (`SalaryComponent`) — voir chaque section ci-dessous et l'entrée `CLAUDE.md` correspondante pour le détail complet.

## Modèles clés

| Modèle | Table DB | Rôle |
|---|---|---|
| `PayrollRun` | `payroll_runs` | Cycle de paie pour un tenant/période (`draft → validated → paid`), totaux agrégés (brut, déductions, net) — **désormais réellement synchronisé** par `approveBatch()`/`processPayment()` (Chantier 32.18, voir Services) |
| `Payslip` | `payslips` | Bulletin de salaire individuel rattaché à un `PayrollRun`, `salary_components` stocké en JSON. Expose désormais de vraies relations `employee()` (`Modules\HR\Models\Employee`) et `payrollRun()` (Chantier 32.18 — aucune des deux n'existait avant, malgré des FK réelles) |

`PayrollRun` expose la relation `payslips()` (hasMany). Ce duo (`PayrollRun`/`Payslip`) est le schéma migré et le seul chemin réellement exposé par l'API — le bug historique documenté ici jusqu'à une refonte antérieure (`PayrollController`/`PayrollIntegrationService` important `Modules\HR\Models\PayrollRecord`/`PayrollPeriod`, deux classes qui n'existaient nulle part dans le dépôt) a été corrigé depuis : `PayrollIntegrationService` opère directement sur `PayrollRun`/`Payslip` et sur la vraie source de salaire (voir Services ci-dessous).

**`SalaryComponent`/table `salary_components` — supprimés (Chantier 32.18)** : un second, entièrement mort moteur de calcul de salaire (catalogue de composants configurables par tenant, jamais consommé par aucun contrôleur/route/page Vue/test) divergent du vrai moteur de production (`PayrollIntegrationService::calculateSalaryComponents()`, piloté par `EmployeeCompensation`+`StatutorySchemes`). Voir la migration `2026_10_16_000001_drop_dead_salary_components_table.php` pour le détail complet du raisonnement.

## Endpoints principaux

Préfixe `/api/v1/payroll/` (`Modules/Payroll/routes/api.php`) :

| Middleware | Méthode | Route | Description |
|---|---|---|---|
| `auth:sanctum, session.security, tenancy.user, module:Payroll, role:hr-manager,payroll-officer,accountant,finance-manager,manager,admin` | GET | `payslips` | Liste des bulletins pour une période (`?period=YYYY-MM`) |
| — | POST | `generate` | Génère les bulletins pour tous les employés actifs d'une période |
| — | POST | `payslips/approve-batch` | Approuve en lot les bulletins brouillon d'une période |
| — | POST | `process-payment` | Traite le paiement des bulletins approuvés + intégration comptable |
| — | GET | `statistics` | Statistiques de paie pour une période |
| — | GET | `taxes/by-country` | Répartition des taxes/cotisations par pays |
| `auth:sanctum, session.security, tenancy.user` (tout utilisateur) | GET | `me/payslips` | Bulletins de l'utilisateur connecté (self-service) |
| — | GET | `payslips/{payslip}` | Détail d'un bulletin — `authorize('view', $payslip)` via `PayrollPolicy` (tout employé peut voir son propre bulletin ; staff paie/hr-manager/admin **de la même société uniquement** depuis Chantier 32.18, voir Sécurité ci-dessous) |
| — | GET | `payslips/{payslip}/export/pdf` | **Nouveau (Chantier 32.18)** — télécharge le « bulletin de paie » réel en PDF (`PayslipExportController`), même garde `PayrollPolicy::view()` |
| `auth:sanctum, session.security, tenancy.user` | POST | `ai/assist` | Guidance IA contextuelle (`PayrollAiAssistController`) — **note (Chantier 32.18) : ce contrôleur dédié n'est atteint par aucun appelant frontend réel**, le composable `useAiAssistant()` poste toujours vers le point d'entrée générique `/api/v1/ai/assist` (`Modules\AI\Http\Controllers\Api\AiAssistantController`), qui délègue à la même `AiContextualAssistantService` — même motif déjà documenté globalement au Chantier 32.2 pour les ~26 autres contrôleurs `<Module>AiAssistController` de l'app ; non supprimé ici (hors périmètre de ce module), mais confirmé pour la première fois côté Payroll |

Correction Chantier 10 : ce groupe (ainsi que le groupe self-service et le groupe IA) n'avait pas de middleware `module:Payroll` dédié, contrairement à tous les modules frères (HR/Timesheets/Projects/Helpdesk) — ajouté pour cohérence (permet notamment de désactiver le module par tenant via `ModuleManager`, ce qu'un simple `role:` ne permettait pas).

Route web (`Modules/Payroll/routes/web.php`, ajoutée cette session — le module n'en avait aucune) : `GET /payroll` → `Inertia::render('Payroll/Dashboard/Index')`.

## Contrôleurs

- **`Api\PayrollController`** — bulletins, génération, approbation par lot, paiement, statistiques, répartition fiscale par pays, self-service (`myPayslips`/`show`). Chaque méthode staff vérifie `$request->user()->can('payroll.payslip.<verb>')` (`abort_unless`) ; `show()` passe par `$this->authorize('view', $payslip)`. **Chantier 32.18** : `approveBatch()`/`processPayment()` synchronisent désormais le `PayrollRun` correspondant via `PayrollService::validateRun()`/`processRun()` (voir Services) ; `approveBatch()` a été converti d'une mise à jour de masse (`Payslip::where(...)->update(...)`, qui ne déclenche jamais les évènements Eloquent) vers une itération+sauvegarde par enregistrement, pour que `PayslipObserver` (nouveau) se déclenche réellement.
- **`Api\PayslipExportController`** — **nouveau (Chantier 32.18)** : `pdf(Payslip $payslip)` génère un vrai « bulletin de paie » PDF (`Barryvdh\DomPDF`, vue `resources/views/payroll/payslip/pdf.blade.php` — au niveau racine du dépôt, pas sous `Modules/Payroll/resources/`, même convention que les exports Accounting/Analytics/Strategy déjà existants) à partir des vraies données du bulletin (`salary_components` JSON déjà stocké), gardé par la même `PayrollPolicy::view()` que `show()`.
- **`Api\PayrollAiAssistController`** — guidance IA contextuelle, passe `module: 'Payroll'` à `AiContextualAssistantService::getGuidance()`, atteignant la vraie table de repli statique du module Payroll (`generate_payslips`/`approve_payroll`/`export_payroll`/`view_dashboard`) — voir la note sur son inatteignabilité frontend réelle dans le tableau des endpoints ci-dessus.

Aucun contrôleur Web dédié : la route `/payroll` rend directement `Payroll/Dashboard/Index` via une closure Inertia.

## Vues (Vue/Inertia)

- **`Dashboard/Index.vue`** (`Modules/Payroll/resources/js/Pages/Dashboard/Index.vue`) — page réelle et auto-alimentée (liste des bulletins, statistiques, répartition fiscale, approbation par lot, traitement du paiement), appelant l'API Payroll réelle. **Chantier 32.18** : les boutons « View Payslip »/« Download » de chaque ligne de bulletin étaient sans aucun gestionnaire de clic (boutons morts) depuis la construction de la page — câblés sur le nouvel export PDF (`downloadPayslip()`, patron `fetch()`→blob déjà établi ailleurs dans l'app, `View` ouvre dans un nouvel onglet, `Download` déclenche un téléchargement de fichier).
- Pas de page dédiée « mes bulletins » côté self-service pour l'instant — `GET me/payslips`/`GET payslips/{payslip}` sont consommés côté HR (`resources/js/Pages/HR/Payroll/Index.vue`, `HR/Portal.vue`) plutôt que par une vue propre au module Payroll.
- **Trouvé mais non corrigé (hors périmètre — fichier partagé hors `Modules/Payroll/**`), Chantier 32.18** : le module Payroll **n'a aucune entrée dans la navigation principale** (`resources/js/Layouts/AppLayout.vue`'s `allNavGroups`) — `ROLE_MODULE_ACCESS['payroll-officer'] = ['Payroll', 'HR']` filtre la *visibilité* d'un élément de menu, mais aucun élément portant `module: 'Payroll'` n'existe dans `allNavGroups` pour être filtré. Le même bug (page réelle, zéro entrée de nav) avait déjà été trouvé et corrigé pour Sales au Chantier 32.16 — Payroll porte le même trou, non corrigé ici puisqu'il exige de modifier un fichier partagé racine hors du périmètre strict de cet audit ; signalé pour un futur chantier ciblé sur ce fichier.

## Services

- **`PayrollService`** — opère sur le schéma actuel (`PayrollRun`/`Payslip`) : `createRun()`, `processRun()`, `validateRun()`, `markAsPaid()`, `getStats()`. `createRun()` est **appelé par `Modules\Workflow\Services\Actions\Phase52ActionHandler::generatePayrollRun()`** (le moteur d'automatisation). **Depuis Chantier 32.18, `processRun()`/`validateRun()` sont aussi réellement appelées par `PayrollController::approveBatch()`/`processPayment()`** — auparavant ces deux méthodes existaient, réelles et fonctionnelles, mais sans aucun appelant : `PayrollRun.status`/`total_gross`/`total_deductions`/`total_net`/`validated_at` restaient figés à `draft`/`0`/`null` pour toujours, même après qu'un cycle complet d'approbation+paiement des bulletins sous-jacents ait eu lieu (confirmé empiriquement via tinker). `markAsPaid()` reste délibérément non réutilisée par `processPayment()` — elle marque directement tout bulletin encore `draft` comme `paid`, ce qui court-circuiterait la règle métier « seuls les bulletins déjà `approved` peuvent être payés » que le contrôleur applique. `getActiveComponents()`/`computeSalary()` — un second moteur de calcul de salaire piloté par le catalogue `SalaryComponent`, confirmé mort (zéro appelant, divergent du vrai moteur de production) — **supprimés** au Chantier 32.18, voir ci-dessus.
- **`PayrollIntegrationService`** — service branché sur `PayrollController`, réécrit cette session pour supprimer sa dépendance envers les classes `Modules\HR\Models\PayrollRecord`/`PayrollPeriod` (absentes du dépôt) : génère les bulletins (`generatePayslips`/`generatePayslip`) directement sur `PayrollRun`/`Payslip`, calcule les composants de salaire, les heures supplémentaires, les allocations et les déductions, et passe les écritures comptables OHADA (`postPayslipsToAccounting()` → `Modules\Accounting\Models\JournalEntry`, imputation Cl.6161/Cl.4210). **Chantier 32.18** : `getPayrollSummary()` calculait un résumé correct mais `PayrollController::statistics()` écrasait systématiquement sa devise réelle par `'XOF'` codé en dur, quelle que soit la vraie devise des bulletins (un bulletin réel en MGA affichait « XOF 525 000 » sur le tableau de bord) — corrigé : `getPayrollSummary()` dérive désormais la vraie devise (bulletins de la période, puis `App\Models\Company::currency`, puis `'XOF'` en dernier repli), et le contrôleur ne l'écrase plus.
  - **Source de salaire réelle** : `base_salary`/`currency` viennent désormais de `Modules\HR\Models\EmployeeCompensation` via un helper `getCurrentCompensation(Employee, Carbon $asOf)` (résolu à la date de début de la période de paie, pas `now()`) — corrige le bug historique où `base_salary`/`monthly_salary` étaient lus directement sur `Employee`, des colonnes qui existent en base mais jamais dans son `$fillable`, ce qui faisait silencieusement calculer un salaire quasi nul sur tout bulletin généré via l'UI/API réelle (seuls les tests passaient, en contournant `$fillable` via `Model::unguarded()`).
  - **Tenant** : `tenant_id` vient de l'appelant (ou, à défaut, de `Employee::user->company_id`) plutôt que du champ fantôme `hr_employees.tenant_id` (jamais alimenté). Correction Chantier 10 : `PayrollController`/`PayrollIntegrationService` lisaient auparavant `Employee::user->tenant_id` — une confusion documentée dans une session précédente comme « la vraie colonne de délimitation multi-tenant », mais `users.tenant_id` est en réalité le même champ fantôme (réel, migré, jamais dans `User::$fillable`, jamais alimenté par le flux d'inscription réel) déjà corrigé ailleurs dans l'app (Reporting, Strategy, AI, Sales, Achats, Integration, Workflow) — chaque tenant voyait donc silencieusement les bulletins de tous les autres tenants s'agréger dans le même panier `tenant_id=0`. Corrigé vers `users.company_id`, la vraie colonne de délimitation. Verrouillé par `Modules/Payroll/tests/Feature/Chantier10PayrollTenantIsolationTest.php` (isolation testée sur le vrai chemin HTTP, deux entreprises distinctes).
  - **Heures supplémentaires** : dérivées des saisies réelles et approuvées de `Modules\Timesheets\Models\TimesheetEntry` (au-delà de 160h/mois), plutôt que de la table `hr_timesheets` (jamais alimentée) lue auparavant.
  - **Allocations granulaires** (`housing_allowance`, `transport_allowance`, `family_allowance`, `monthly_bonus`) restent lues sur des champs `Employee` qui n'ont pas de source de données réelle par employé dans cette version — laissées à `?? 0` (repli documenté, pas un bug corrigé silencieusement).
  - **Remboursement de prêt** (`calculateLoanRepayment()`) reste à 0 — aucune fonctionnalité de gestion de prêts salariés n'existe nulle part dans le dépôt.
- **`Data\StatutorySchemes`** (`app/Data/`) — table de données statiques des régimes de cotisations sociales et de l'impôt sur le revenu pour 8 pays africains (SN, CI, CM, MG, BJ, TG, BF, ML) : tranches d'IR progressives, abattements, surtaxes, minimums statutaires, régimes de cotisations sociales avec taux et plafonds, catégorisés (`pension`/`social_security`/`health`/`combined`). **Désormais réellement câblée** : `calculateIncomeTax()` exécute un vrai calcul par tranches progressives pour ces 8 pays (`calculateProgressiveIncomeTax()`), avec repli sur l'ancienne approximation à taux forfaitaire pour les pays hors de ce jeu de données (dont NG) ; `calculateSocialSecurity()`/`calculatePensionContribution()` sommes les régimes réels par catégorie sans double comptage.
- **`PayrollPolicy`** — corrigée : la vérification « bulletin personnel » comparait `$model->employee_id` (un `hr_employees.id`) directement à `$user->id` (un `users.id`), empêchant tout employé de passer le contrôle sur son propre bulletin ; compare désormais `$user->employee->id`. Le rôle inexistant `payroll-manager` a été remplacé par le vrai rôle `payroll-officer`. Désormais enregistrée auprès du Gate via `PayrollServiceProvider::registerPolicies()` (`Gate::policy(Payslip::class, PayrollPolicy::class)`) — les policies namespacées sous `Modules\*` ne s'auto-découvrent pas. **Chantier 32.18 (IDOR cross-tenant réelle, la découverte la plus sévère de cet audit)** : `view()`/`export()` accordaient un accès complet à **n'importe quel** bulletin, de n'importe quelle société, à tout utilisateur portant le rôle `hr-manager`/`payroll-officer`/`admin` — confirmé empiriquement via tinker (`$userB->can('view', $payslipA)` valait `true` alors que `$userB` appartenait à une société différente de celle du bulletin). `PayrollController::show()` n'a aucune autre vérification de société de son côté. Corrigé avec un vrai contrôle `sameCompany()` (`$model->tenant_id === $user->company_id`, deux colonnes `integer` — pas de conversion de type nécessaire, contrairement au motif `string(36)` déjà documenté pour Security) ; `super-admin` reste correctement exempté via `Gate::before` (`AppServiceProvider`), donc n'a jamais eu besoin de cette branche.
- **`PayslipObserver`** — **nouveau (Chantier 32.18, couche 11 CORE)** : Payroll n'avait jamais été câblé sur `Modules\Core\Services\ParticipantNotificationService` (la règle app-wide du Chantier 20 « notifier tout participant + le supérieur hiérarchique direct de l'auteur de l'action ») — un employé n'était notifié ni de l'approbation ni du paiement de son propre bulletin. Réagit à la transition `status → approved|paid` (`updated()`), notifie l'employé (`payslip->employee?->user`), auteur résolu via `Auth::user()` (même convention d'acteur déjà établie pour `TicketObserver` au Chantier 20). Enregistré dans `PayrollServiceProvider::boot()`.

## Permissions RBAC

Préfixe `payroll.*` dans `RolesAndPermissionsSeeder::MODULES` : ressources `payslip`, `run`, `tax-config`, actions standard `view-any|view|create|update|delete`. Le rôle `hr-manager` reçoit toutes les permissions `payroll.*` ; le rôle `payroll-officer` aussi.

`PayrollController` vérifie en réalité des chaînes ad hoc (`payroll.payslip.view`, `.generate`, `.approve`) plutôt que le schéma générique `payroll.<resource>.<action>` du seeder — ces chaînes sont bien réelles/seedées (`payslip` est une ressource déclarée), donc les vérifications fonctionnent pour les rôles porteurs de `payroll.*`. Correction RBAC de cette session : le groupe de routes n'incluait pas `payroll-officer` — le rôle nommé pour ce module était bloqué à la porte d'entrée avant même la vérification de permission — et `statistics()`/`taxesByCountry()` n'avaient aucun `authorize()`/`abort_unless()` du tout, permettant à `accountant`/`finance-manager` (qui n'ont pas `payroll.*`) de lire ces agrégats en ne passant que la grille de rôles au niveau route ; les deux ont été corrigés (rôle ajouté au groupe, `abort_unless` ajouté aux deux méthodes).

## Dépendances avec d'autres modules

- **HR** : `PayrollIntegrationService` importe désormais `Modules\HR\Models\Employee` et `Modules\HR\Models\EmployeeCompensation` (la vraie source de salaire, construite par `Modules\HR\Services\CompensationService`) — la dépendance envers les classes inexistantes `PayrollRecord`/`PayrollPeriod` a été supprimée. Inversement, HR consomme `Modules\Payroll\Models\Payslip` en lecture pour son self-service (voir `docs/03-MODULES/HR.md`).
- **Timesheets** : `PayrollIntegrationService::calculateOvertime()` lit `Modules\Timesheets\Models\TimesheetEntry` (heures approuvées) pour dériver les heures supplémentaires.
- **Accounting** : `PayrollIntegrationService::postPayslipsToAccounting()` crée des `Modules\Accounting\Models\JournalEntry` (comptabilisation OHADA du salaire brut et du net à payer).
- **AI** : `PayrollAiAssistController` utilise `AiContextualAssistantService`.
- **Workflow** : `Phase52ActionHandler` (module Workflow) déclenche `PayrollService::createRun()` via l'automatisation cross-module.

## Particularités du périmètre life-mdg-erp

- **Les deux implémentations parallèles documentées avant cette refonte n'existent plus** : le schéma migré (`PayrollRun`/`Payslip`, piloté par `PayrollService`) est désormais réellement utilisé aussi bien par le moteur d'automatisation Workflow (`createRun()`) que par le chemin exposé par l'API REST (`PayrollController` → `PayrollIntegrationService` pour la génération/lecture, `PayrollService::validateRun()`/`processRun()` pour la synchronisation du cycle de paie depuis Chantier 32.18) — les deux convergent sur le même `PayrollRun`/`Payslip`. Le troisième composant (`SalaryComponent`, un catalogue de composants configurables jamais consommé nulle part) a été confirmé mort et supprimé au Chantier 32.18, pas juste documenté comme un second point d'entrée orphelin.
- **Répartition fine des primes/allocations non modélisée** : seule une valeur agrégée (`base_salary`, `bonus_amount`, `benefits_annual_value`) existe par employé sur `EmployeeCompensation` — les sous-catégories (logement, transport, famille, prime mensuelle) restent à 0 par défaut, faute de source de données dédiée, plutôt que d'inventer une répartition arbitraire.
- **Gestion de prêts salariés absente** : `calculateLoanRepayment()` retourne toujours 0, faute de tout modèle/contrôleur/UI de prêt employé dans ce dépôt — documenté comme gap plutôt que masqué.
- **Aucune entrée dans la navigation principale** (`AppLayout.vue`) — voir la section Vues ci-dessus ; page réelle, atteignable uniquement par URL directe (`/payroll`).
- **`PayrollAiAssistController` inatteignable par le frontend réel** — voir la section Endpoints ci-dessus ; le composable `useAiAssistant()` poste toujours vers le point d'entrée générique de `Modules\AI`, jamais vers ce contrôleur dédié. Sans conséquence fonctionnelle (les deux chemins délèguent à la même `AiContextualAssistantService`, déjà correctement enregistrée pour `'Payroll'`), mais du code mort du point de vue du trafic réel.
