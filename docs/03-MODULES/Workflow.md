# Workflow

## Rôle

Le module Workflow est le moteur d'automatisation métier de Life MDG ERP : il permet de définir des chaînes « déclencheur → conditions → actions » qui réagissent aux événements des autres modules (ex. `crm.opportunity.won`) et exécutent des actions dans Accounting, HR, Inventory, Helpdesk, etc. Il coexiste avec un second sous-système « flow builder » façon n8n (`AutomationFlow`, `FlowExecutionEngine`) — désormais réellement exposé par API REST depuis le Chantier 32.11 (voir Particularités), pas seulement présent en base de code. Un troisième bloc de routes — un ancien moteur de builder/tâches/approbations (`WorkflowController@create`/`getCanvas`/etc., `ExecutionController`, `TaskController`, `ApprovalController`) — avait été **supprimé** au Chantier 8.5-light (voir Particularités) : ces classes n'existaient nulle part dans le module, le bloc de ~34 routes était fatal au premier appel.

Les tables sont créées par les migrations racine (`database/migrations/2026_05_17_*workflow*`, `*automation*`, patches `wave15`–`wave26`), pas par des migrations propres au module — sauf les patchs de colonnes ajoutés au fil des chantiers (`Modules/Workflow/database/migrations/`), qui, eux, sont bien propres au module.

**Important — `automation_flows.nodes`/`.edges` sont des colonnes ET des noms de méthode de relation** : `AutomationFlow` a une colonne réelle `nodes` (JSON, jamais utilisée par le vrai code, un résidu de schéma) en plus de sa relation `nodes(): HasMany`. L'accès PHP par propriété (`$flow->nodes`, sans parenthèses) retourne toujours la colonne brute — jamais la relation, même après un `->load('nodes')` explicite — c'est le même piège de collision colonne/relation déjà documenté ailleurs dans ce dépôt (`Product::category` en Inventory). La sérialisation JSON (`response()->json($flow->load(['nodes', ...]))`) reste correcte car `Model::toArray()` fait gagner les relations chargées sur les attributs lors de la fusion finale — seul un futur accès PHP direct par propriété serait piégé. Confirmé sans impact réel aujourd'hui (aucun contrôleur n'accède `$flow->nodes` en PHP hors `load()`/JSON), documenté comme point de vigilance pour un futur chantier plutôt que corrigé (renommer une colonne DB réelle est un changement plus lourd qu'un simple renommage de méthode).

## Vues (Vue/Inertia)

**Aucune route web, aucune page Vue** (`Modules/Workflow/routes/web.php` n'existe pas, `Modules/Workflow/resources/` n'existe pas non plus). Les deux pages mock documentées par les chantiers précédents (`AIWorkflowBuilder/Index.vue`, `RPA/Index.vue`) ont en réalité été **supprimées pour de bon au Chantier 9** (nettoyage des pages 100 % mock) — les notes des chantiers ultérieurs les décrivant comme « laissées en l'état, 100 % mock » étaient stales, confirmé par recherche directe sur disque au Chantier 32.11. Le module est donc aujourd'hui un **module API pur** : un vrai moteur n8n-like complet et désormais entièrement routé (Chantier 32.11), sans aucune interface visuelle de construction de flow — construire un vrai builder drag-and-drop reste un chantier frontend distinct, de taille comparable, non entrepris ici.

## Services

- **`WorkflowEngineService`** — le moteur réel Phase-39 : `executeWorkflow()` (point d'entrée, résout les `WorkflowChainDefinition` actives pour une `trigger_key`), `runDefinition()`, `executeAction()` (dispatcheur central par préfixe de module — voir Particularités pour le bug corrigé au Chantier 32.11), `evaluateConditions()`/`evaluateCondition()`. Les méthodes legacy Cache-based (`createWorkflow`/`addStep`/`publishWorkflow`/`getWorkflow`/`getExecution`/`deleteWorkflow`/`duplicateWorkflow`/`evaluateTrigger`/`dispatchAction`/`processChain`/`dispatchParallelActions`/`dispatchWithRetry`/`dispatchWithTimeout`/`logExecution`) ont été **supprimées au Chantier 32.11** — zéro appelant réel confirmé, même motif que les 3 services ci-dessous.
- **`Automation\FlowExecutionEngine`** — moteur de flow façon n8n : `execute()` traverse le graphe de nœuds d'un `AutomationFlow`, `evaluateConditionExpr()`, `pause()`/`resume()`/`retry()`, et `triggerByKey()` (point d'entrée documenté pour déclencher un flow depuis n'importe quel autre module, ex. `crm.opportunity.won`). Le nœud de code sandboxé (`executeCodeNode()`) applique désormais un vrai `ulimit` (voir Particularités).
- **`Automation\NodeTypeRegistry`** — registre central de tous les triggers/actions (`getAll()`, `getByModule()`, `getActionsForModule()`), avec libellés en français.
- **`Automation\FlowSchedulerService`** — planification cron des flows, seule source de vérité pour le stockage (`trigger_config['cron']`).
- **`Automation\AiWorkflowAssistantService`** — suggestion/génération/validation de règles via Claude, fallback-first — **branchée pour de vrai au Chantier 32.11** (auparavant réelle, écrite, mais zéro consommateur nulle part).
- **`WorkflowDslParser`** / **`WorkflowJsonSchema`** — parseur du DSL français (SI/QUAND/ALORS) et validation JSON Schema associée.
- **`CodeNodeService`** — exécution sandboxée d'un nœud de code/expression, homologue autonome de `FlowExecutionEngine::executeCodeNode()` pour l'API REST `code-node/*`.
- **`FlowVersionService`** — snapshot/restore de versions de flow.
- **`WorkflowActionRegistry`** — registre secondaire prefix→handler pour les 18 handlers d'action réels ; **corrigé au Chantier 32.11** (voir Particularités — le constructeur ne déclarait que 3 paramètres alors que le provider en passait 18, un `TypeError` fatal garanti sur toute résolution).
- **Handlers d'action** (`app/Services/Actions/`, un par domaine, chacun implémentant `dispatch(string $action, array $params, array $context): array`, enregistrés en singleton dans `WorkflowServiceProvider`) : `AchatsInventoryActionHandler`, `CrmSalesActionHandler`, `HrPayrollActionHandler`, `InventoryAccountingActionHandler`, `SalesManufacturingActionHandler`, `NotificationActionHandler`, `AiActionHandler`, `CalendarActionHandler`, `DataTransformHandler`, `DelayActionHandler`, `DocumentsActionHandler`, `EcommerceActionHandler`, `HelpdeskActionHandler`, `HttpActionHandler`, `LogisticsActionHandler`, `ProjectsActionHandler`, `QualityActionHandler`, `StrategyActionHandler`. Les 12 derniers (« nouveau lot ») sont désormais réellement atteignables via `WorkflowEngineService::executeAction()` — voir Particularités.

**Supprimés au Chantier 32.11 (confirmé zéro appelant réel, même motif que la « Legacy Workflow Engine » supprimée au Chantier 8.5-light)** : `ApprovalWorkflowService` (identifiants `uniqid()`, aucun modèle Eloquent, `Cache`-backed — le point de départ de cet audit), `TaskManagementService` (même motif), `WorkflowBuilderService` (même motif — canvas visuel pour le moteur legacy Cache-based, lui aussi supprimé).

## Permissions RBAC

Workflow n'a **pas** d'entrée dans `RolesAndPermissionsSeeder::MODULES` (contrairement à `crm`, `sales`, `accounting`, etc.) — aucune permission granulaire `workflow.*.*` n'est réellement seedée. L'accès est contrôlé autrement :
- **tout le fichier `routes/api.php`** (hors AI-assist et le webhook public) est protégé par `module:Workflow`+`role:manager,admin`, au niveau du groupe englobant plutôt que route par route ;
- les policies (`WorkflowDefinitionPolicy`, `WorkflowExecutionPolicy`) vérifient `$user->hasAnyRole(['workflow-manager', 'admin', 'super-admin'])`, avec un fallback `hasPermissionTo('workflow.definition.create')` etc. — ce fallback référence des permissions qui n'existent pas dans le seeder actuel, et le rôle `workflow-manager` lui-même n'est pas défini dans `RolesAndPermissionsSeeder`. **Ni l'une ni l'autre policy n'est enregistrée sur le Gate et aucun contrôleur ne les appelle** (`authorize()` : zéro occurrence dans tout `Http/Controllers/`) — confirmé au Chantier 32.11, laissé en l'état délibérément : le module s'appuie uniquement sur le gate de route + le cloisonnement par tenant au niveau requête (`WorkflowDefinition::forTenant()`, `AutomationFlow::forTenant()`, etc.), le même motif que `TerritoryController`/`RateLimitController` ailleurs dans l'app (« pas de modèle naturel pour accrocher une policy par enregistrement, gate de rôle au niveau route suffisant ») — un vrai gap de granularité, mais pas un trou de sécurité en soi puisque le gate de route + le scoping par tenant tiennent déjà. Câbler ces 2 policies nécessiterait de seeder de nouvelles permissions dans `RolesAndPermissionsSeeder.php`, hors du périmètre chirurgical de ce chantier (racine partagée, pas propre au module).

## Dépendances avec d'autres modules

Workflow est un **hub d'intégration** : ses handlers d'action importent directement les modèles/services d'Accounting, Helpdesk, CRM (via `HelpdeskActionHandler` qui utilise `Modules\Helpdesk\Models\Ticket`, `TicketService`, `EscalationService`, `TicketAssignmentService`), et d'autres domaines métier. `NotificationActionHandler::sendInAppNotification()` délègue au vrai `App\Services\NotificationService` (Chantier 20) plutôt que d'écrire dans la table `notifications` avec des colonnes inventées. Aucun autre module de life-mdg-erp n'importe `Modules\Workflow` directement dans son code PHP (`Strategy\StrategyObjectiveLink`, `Helpdesk\HelpdeskServiceProvider`, `Payroll\PayrollService`/`PayrollIntegrationService`, `HR\Employee`, `Calendar\ModuleEventAggregatorService` ne le référencent que par commentaire/docblock) — les autres modules déclenchent des chaînes indirectement via `FlowExecutionEngine::triggerByKey()` appelé depuis leurs propres services/écouteurs d'événements plutôt que par un import statique.

## Particularités du périmètre life-mdg-erp

- **Chantier 32.11 — audit approfondi en 14 couches, décision principale : `ApprovalWorkflowService` supprimé pour de bon**. Reconfirmé empiriquement (grep des appelants + relecture directe) exactement comme le Chantier 31 l'avait déjà établi : identifiants `uniqid('approval_')`, aucun modèle Eloquent réel, `Cache::put()` comme seule persistance, zéro appelant réel hors ses propres tests. `Modules\Validation` est déjà le vrai moteur d'approbation de l'app (Achats/Accounting/HR). Supprimé avec sa liaison singleton/alias (`'approval_workflow'`) dans `WorkflowServiceProvider` et ses 4 fichiers de test isolés (réécrits/supprimés, pas laissés à échouer).
- **Le même motif trouvé deux fois de plus, supprimé pour de bon** : `TaskManagementService` et `WorkflowBuilderService` — mêmes symptômes exacts (`Cache`-backed, `uniqid()`, zéro modèle, zéro appelant réel), confirmés indépendamment par grep avant suppression.
- **Un bug de constructeur garanti fatal trouvé et corrigé — `WorkflowActionRegistry` ne pouvait jamais être résolu du conteneur** : son constructeur ne déclarait que 3 paramètres (`AchatsInventoryActionHandler`, `InventoryAccountingActionHandler`, `NotificationActionHandler`) alors que `WorkflowServiceProvider`'s `singleton(WorkflowActionRegistry::class, fn ($app) => new WorkflowActionRegistry(...))` lui passait déjà 18 arguments positionnels — PHP lie les arguments positionnels en excès par position, pas par nom, donc l'argument #2 (`CrmSalesActionHandler`) était forcé dans le paramètre `$inventoryAccountingHandler` (typé `InventoryAccountingActionHandler`) → `TypeError` fatal garanti, confirmé empiriquement via `app(WorkflowActionRegistry::class)` avant correctif. Corrigé en étendant le constructeur aux 18 handlers réels, dans l'ordre exact déjà passé par le provider, et en enregistrant les 12 handlers du « nouveau lot » sous leurs vrais préfixes de clé d'action.
- **Un second bug, plus profond, trouvé en corrigeant le premier — 12 handlers d'action réels totalement inatteignables en production** : `WorkflowEngineService::executeAction()` — le vrai dispatcheur utilisé par `runDefinition()` (chaque exécution réelle de `WorkflowChainDefinition`), par `WorkflowDefinitionController::test()` (dry-run) et par `WorkflowExecutionController::retry()` — n'avait **aucun** `case` pour les préfixes `ai`/`calendar`/`transform`/`delay`/`documents`/`ecommerce`/`helpdesk`/`http`/`logistics`/`projects`/`quality`/`strategy`, malgré leurs 12 handlers réels, écrits, enregistrés en singleton dans le provider. Toute action réelle utilisant l'un de ces préfixes tombait silencieusement dans la branche `default => "Unknown action module"`, confirmé empiriquement avant correctif. Corrigé en ajoutant les 12 cas manquants, chacun délégant à `app(<Handler>::class)->dispatch($actionKey, $params, $context)` — même convention déjà utilisée pour `hr`/`it`/`payroll` (clé d'action complète, pas seulement le préfixe).
- **Chantier 32.11 — 5 contrôleurs réels réellement branchés pour la première fois** (`AutomationFlowController`, `WorkflowScheduleController`, `WorkflowTemplateController`, `AiWorkflowController`, `WorkflowNodeController`) — documentés comme un « écart volontairement laissé, effort de taille comparable à la reconstruction BI » depuis le Chantier 19 Lot 3. Vérifiés empiriquement avant le routage (pas seulement relus), ce qui a révélé 3 bugs supplémentaires, tous corrigés avant publication des routes :
  - **`WorkflowScheduleController` lisait/écrivait `$flow->schedule_config`, une colonne qui n'a jamais existé sur `automation_flows`** (confirmé via `Schema::getColumnListing()`) et absente de `AutomationFlow::$fillable` — chaque appel réel à `update()` était donc un no-op silencieux (assignation de masse Eloquent ignore silencieusement une clé absente de `$fillable`). Le vrai planificateur (`FlowSchedulerService`) lit/écrit exclusivement `trigger_config['cron']`, une colonne réelle déjà `$fillable`/castée. Corrigé pour utiliser `trigger_config` partout, avec `trigger_type` forcé à `'schedule'` lors de la mise à jour (nécessaire, sinon `FlowSchedulerService::schedule()`'s propre garde `if ($flow->trigger_type !== self::SCHEDULE_TRIGGER) return;` no-opait quand même).
  - **`WorkflowTemplateController` validait/écrivait `nodes`/`connections`/`config` comme colonnes plates alors que `AutomationFlowTemplate::$fillable` n'a qu'un seul champ JSON `flow_definition` (NOT NULL) portant tout le payload** — chaque `store()` réel était une violation de contrainte NOT NULL garantie, confirmée empiriquement (pas une simple relecture). `index()`'s filtre `module` référençait une colonne inexistante (seul `category` existe), et `preview()` lisait `$template->nodes`/`$template->connections` — des accesseurs qui n'existent pas du tout sur ce modèle. Réécrit pour construire/lire `flow_definition` correctement, exactement la forme déjà attendue par `AutomationFlowTemplate::instantiateForTenant()`.
  - **`NotificationActionHandler::sendEmail()`/`sendInAppNotification()`/`sendSms()` passaient un `$tenantId` non typé (`$context['tenant_id'] ?? 1`) à des méthodes privées `resolve*(array $targets, int $tenantId)` avec un typage strict `int`** — puisque ce module utilise majoritairement des `tenant_id` en chaîne (`WorkflowChainController::tenantId(): string`, `WorkflowChainDefinition.tenant_id`), tout appel réel avec un contexte `tenant_id` en chaîne levait un `TypeError` fatal, confirmé empiriquement (pas une hypothèse — une vraie exécution de chaîne avec une action `notify.in_app` échouait avant ce correctif). Corrigé en castant `(int)` à l'extraction du contexte dans les 4 sites concernés.
  - `AutomationFlowController::webhookTrigger()` (déclencheur webhook entrant, conçu pour être public par son propre docblock) est routé hors du groupe `auth:sanctum`, limité par `throttle:webhook` — même patron déjà établi ailleurs dans l'app pour les webhooks publics.
  - `WorkflowScheduleController::due()` (liste les flows dus « maintenant ») est délibérément scopé au tenant appelant malgré `FlowSchedulerService::getDueFlows()` étant intentionnellement cross-tenant en interne (le vrai dispatcheur cron a besoin de voir tous les tenants) — exposer la sortie brute du service via cet endpoint HTTP, gardé par le rôle ordinaire `manager,admin` (pas super-admin), aurait fui les flows planifiés de toutes les autres sociétés.
- **Durcissement réel du nœud de code sandboxé (`python_safe`)** : `CodeNodeService::runPythonSafe()` et `FlowExecutionEngine::executeCodeNode()` documentaient tous deux « ulimit -v (64MB mémoire), -t (CPU 5s) » comme garantie de sécurité déjà en place — **aucun appel `ulimit` n'existait réellement dans la commande construite**, confirmé en lisant puis en exécutant le code. Corrigé en ajoutant un vrai `ulimit -v 65536; ulimit -t <timeout>` avant l'exécution de `python3` (deux appels séparés — `sh` sur les conteneurs cibles de cette app est `dash`, qui rejette la syntaxe combinée `-v X -t Y` propre à `bash`, confirmé empiriquement). Vérifié via une vraie tentative d'épuisement mémoire : passe de 5s (timeout complet) à 0,06s (tuée quasi instantanément par le ulimit) après correctif. **Risque résiduel documenté, non résolu — hors périmètre d'un chantier chirurgical** : la liste noire par expression régulière (`BLOCKED_PATTERNS`, ~17 motifs) contre un interpréteur Python arbitraire n'est **pas** une vraie frontière de sandbox — c'est une catégorie de vulnérabilité bien connue (contournable, ex. `().__class__.__base__.__subclasses__()` pour atteindre `subprocess.Popen` sans jamais utiliser aucun des mots-clés bloqués). Une vraie solution nécessiterait un conteneur/microVM/seccomp dédié, ou l'abandon de `python_safe` au profit du langage `expression` (prouvé sûr par construction — aucun interpréteur, un évaluateur récursif écrit à la main sans `eval()`/`exec()` d'aucune sorte, vérifié par lecture complète du code).
